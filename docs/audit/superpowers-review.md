## Findings

| Severity | file:line | Problem | Concrete fix |
|---|---|---|---|
| Critical | backend/app/models/pickup.rb:3, frontend/src/App.jsx:4 | The status flow does not match ITAD. There is no data-wipe step, which is the step Revivn customers pay for and need proof of. The flow is also a straight line that always ends in `donated`, and `refurbished` always comes before `donated`. Real outcomes branch after the wipe: resell, donate or recycle. Interviewers at Revivn will see this right away. The README (line 151) even lists "add `wiped`" as future work. | Model the flow as allowed transitions, not an ordered list: `TRANSITIONS = { "scheduled" => %w[picked_up cancelled], "picked_up" => %w[received], "received" => %w[wiped], "wiped" => %w[refurbished recycled], "refurbished" => %w[resold donated] }`. Validate `TRANSITIONS.fetch(status_was, []).include?(status)`. Mirror the same map in App.jsx and render the next allowed actions as buttons. |
| Critical | backend/app/models/pickup.rb:16-21 | Steps can be skipped. The only check is "not backward", so `scheduled → donated` is accepted (verified with runner). The batch is never picked up or wiped, which breaks chain of custody. README:142 claims this "matches a chain of custody". | Allow only the next state(s): `errors.add(:status, ...) unless allowed_next.include?(status)`. Add model and controller tests for `scheduled → donated` being rejected. |
| Critical | frontend/src/App.jsx:246-251 | Every future step is a live button with no confirmation. One misclick on the 4th bar marks a scheduled batch as `donated`. Because backward moves are blocked (pickup.rb:19) and there is no edit, the mistake can't be undone. The only way out is deleting the record. | Show only one "Advance to <next>" button per row, with `window.confirm` for terminal states. If you keep a stepper, set `disabled={i !== current + 1}`. |
| Critical | backend/app/controllers/pickups_controller.rb:49, backend/app/models/pickup.rb:11 | `status` is permitted on create, and the ordering check only runs `on: :update`. `POST /pickups {status:"donated"}` creates a batch that is already donated (verified: valid). | Use a separate `create_params` without `:status`, or `validate :starts_scheduled, on: :create`. Add a controller test. |
| Important | frontend/src/App.jsx:69, 84, 95, 102 | Stale closures: `setPickups([...pickups, ...])`, `pickups.map`, `pickups.filter` and `setForm({...form})` use the `pickups`/`form` captured at render time. Advance row A, then row B before A's PATCH returns: B's update is written over a list where A is still old, so A's change disappears from the UI until reload. A delete during a create has the same problem. | Use functional updaters: `setPickups(prev => prev.map(...))`, `setPickups(prev => [...prev, pickup])`, `setPickups(prev => prev.filter(...))`, `setForm(prev => ({...prev, [field]: value}))`. |
| Important | frontend/src/App.jsx:85-87 | `changeStatus` swallows the 422 body. The server's real reason (e.g. "can't go from picked_up back to scheduled") becomes "Try again", and retrying will fail the same way. The row also keeps showing local state that may be stale (e.g. changed in another tab). | `catch (err) { setActionError(err.fields?.status?.join(', ') ?? "Couldn't update the status."); if (err.fields) loadPickups() }`. |
| Important | backend/app/models/pickup.rb:9 | No past-date validation. A pickup can be scheduled for 2001-01-01 (verified). The date input also has no `min` (App.jsx:198). | `validate :pickup_date_not_in_past, if: -> { new_record? \|\| pickup_date_changed? }` comparing with `Date.current`. Set `config.time_zone` explicitly; it is UTC today, so near midnight the server's "today" differs from a US user's. On the client, build `min` from local date parts (not `toISOString()`, which is UTC). |
| Important | backend/app/controllers/pickups_controller.rb:6 | `ordered_by_date.limit(200)` returns the **200 oldest** pickups. Once data grows, upcoming pickups (the ones ops care about) drop out of the list, and the "newest first" toggle (App.jsx:117-121) only re-sorts those oldest 200. The summary totals (App.jsx:106-114) are computed from the truncated list but labelled as overall totals. | Default to upcoming/active first (e.g. `where(status: active).order(:pickup_date)`) or `order(pickup_date: :desc)`. Add `page`/`status` params, and return the total count (header or `{ pickups:, total: }`) for the summary. |
| Important | backend/app/controllers/pickups_controller.rb:37-39 | Any pickup can be hard-deleted, including `donated`/`refurbished` ones. That destroys the custody record an ITAD company has to keep. | Allow destroy only while `scheduled` (otherwise return 422). Better: add a `cancelled` status and drop hard delete from the UI. Test it. |
| Important | frontend/src/App.jsx (no edit path) | There is no way to edit company, device count or date. With backward moves blocked, every typo or reschedule means delete and recreate, which loses the id and history. `PATCH` already supports it on the backend (pickups_controller.rb:28-34). | Add an inline "Edit" row form (allowed only while `scheduled`) that reuses `api(..., 'PATCH')` and the fieldErrors rendering. |
| Important | backend/db/seeds.rb:7-8 | Seed data contradicts itself. Today is 2026-11-01, yet Globex (2026-11-02) and Pinecrest (2026-11-03) are already `picked_up`, i.e. picked up in the future. All dates are hard-coded, so the demo goes stale. | Use relative dates (`Date.current - 12`, `Date.current + 5`, ...), so `picked_up`/later states are always in the past and `scheduled` ones in the future. Optionally add a model rule: `picked_up` requires `pickup_date <= Date.current`. |
| Important | frontend/src (no tests) | The frontend has zero automated tests (the README admits this, line 134). The stale-state, 422-display and stepper bugs above are exactly what a few tests would catch. For a React role this is a visible gap. | Add Vitest + @testing-library/react with fetch mocked: (1) create shows field errors on 422, (2) two quick status changes both stick, (3) delete removes the row. |
| Important | backend/test/controllers/pickups_controller_test.rb (gaps) | Tests pin the current wrong behaviour by omission. Nothing covers create-with-status, skipping steps, deleting a non-scheduled pickup, the `limit` returning the oldest rows, or a missing `pickup` root key (`params.expect` raises ParameterMissing, which ApplicationController doesn't map to JSON). | Add those cases (each fails today) alongside the model/controller fixes. Add `rescue_from ActionController::ParameterMissing` in application_controller.rb, rendering `{ error: }` with 400. |
| Important | README.md:9, 142 | README:142 says forward-only ordering "matches a chain of custody, where a donated laptop can't go back", but line 9 says steps can be skipped. Skipping (scheduled → donated without pickup or wipe) is a chain-of-custody break, so the README contradicts itself. | Rewrite after fixing the transitions: "each step must follow the previous one; enforced by `Pickup::TRANSITIONS`". |
| Important | README.md:11 | The README says "Validation errors from Rails are shown under each form field". That is true only for the create form. Status-change validation errors are discarded (App.jsx:85-86). | Fix the code (see the changeStatus row) or narrow the claim to "on the create form". |
| Minor | frontend/src/App.jsx:74 | Any non-422 failure (including a 500 or 404) shows "The server didn't respond", which is wrong when it did respond. Old `fieldErrors` also stay on screen after a network error. | Use the message from `api()` (`err.message` includes the status), and call `setFieldErrors({})` in the else branch. |
| Minor | frontend/src/App.jsx:94-97 | Deleting a pickup that is already gone (404, e.g. deleted in another tab) shows "Try again", and every retry 404s again. | Treat 404 on DELETE as success and remove the row. Do the same on PATCH 404: remove the row and show a notice. |
| Minor | frontend/src/App.jsx:61 | The initial load has no abort/cleanup. Under StrictMode (main.jsx:7) it fires twice in dev, and a slow first response could overwrite a newer one. | Use an `AbortController` in the effect with cleanup `() => ctrl.abort()`, passing `signal` through `api()`. |
| Minor | frontend/src/App.jsx:237, 249 | `aria-pressed` on action buttons misstates their meaning (they are not toggles). If `p.status` is unknown, `current = -1` and every step is enabled. | Minor | frontend/src/App.jsx (missing) | No filter by status or company search. Fine with 10 rows, but this is the first thing an ops user asks for. | Add a status `<select>` that filters `sorted` client-side. Move it server-side when pagination lands. |

| Minor | frontend/src/App.jsx:189 | The device input has `min="1"` but no `max="10000"` or `step="1"`, even though the model caps it at 10,000 (pickup.rb:8). | Add `max="10000" step="1"`. |
| Minor | frontend/src/App.jsx:139 | The action-error banner can't be dismissed and there is no success feedback after scheduling. The new row may be off-screen. | Add a dismiss button and a short "Scheduled Acme Corp for Nov 5" status message (`role="status"`). |
| Minor | backend/app/controllers/pickups_controller.rb:8, 13 | No serializer: `render json: @pickup` dumps every column. Any new column (e.g. internal notes) leaks automatically. | Minor | backend/db/seeds.rb:14 | Idempotency is keyed on `company`, which isn't unique. Re-seeding after a user adds a second "Acme Corp" pickup silently skips it, and a seed's changed status/date is never applied. | Key on `company` + `pickup_date`, or `delete_all` in dev before seeding. |

## Top 5

1. **The status flow is wrong for ITAD** (pickup.rb:3): no data-wipe step, and a linear chain that always ends in `donated` instead of branching to resell, donate or recycle.
2. **Steps can be skipped** (pickup.rb:16-21): scheduled → donated is accepted, which breaks chain of custody and contradicts README:142.
3. **One misclick is irreversible** (App.jsx:246-251): any future step is clickable with no confirmation, and with no edit and no backward moves the only fix is deleting the record.
4. **Create accepts `status`** (pickups_controller.rb:49): a pickup can be created already `donated`.
5. **Stale-closure state updates** (App.jsx:69/84/95/102): concurrent actions overwrite each other in the UI. The 422 reason is also swallowed on status changes (App.jsx:85).
